💥 Phase 2 Cryptographic Attack & Defense Simulator

          

            Test classic JWT exploits against the server. Watch the difference between a naive verifier (which trusts token headers blindly) and the hardened verifier (which enforces strict RS256 pinning and claim validation).
          

        

        
      


      

        
        

          

            
EXPLOIT 1

            
Signature Stripping (alg: "none")

          

          

            An attacker crafts a token claiming roles: ["admin"] and changes the JOSE header to {"alg": "none"}, removing the signature entirely.
          


          

            {"alg": "none", "typ": "JWT"}.{"sub": "mallory", "roles": ["admin"]}.<empty>
          


          

            

              Naive Verifier: 💥 VULNERABLE (accepts unsigned token!)
            

            

              Secure Verifier: 🛡️ PROTECTED (pinned to RS256, rejects none)
            

          


          
        


        
        

          

            
EXPLOIT 2 (CVE-2015-9235)

            
RSA Public Key Confusion (alg: "HS256")

          

          

            The attacker fetches the server's public key PEM from JWKS, crafts a token with alg: "HS256", and signs it using the public key as the HMAC secret!
          


          

            HMAC-SHA256(header.payload, secret = Server_Public_RSA_PEM)
          


          

            

              Naive Verifier: 💥 VULNERABLE (treats public key as HMAC secret!)
            

            

              Secure Verifier: 🛡️ PROTECTED (rejects HMAC on RS256 endpoint)
            

          


          
        


        
        

          

            
EXPLOIT 3

            
Payload Claim Tampering

          

          

            Takes Alice's legitimate token (roles: ["User"]) and manually edits the payload base64 to roles: ["admin"] without re-signing.
          


          

            Original_Header.Base64({"roles": ["admin"]}).Original_Signature
          


          

            

              Secure Verifier: 🛡️ PROTECTED (InvalidSignatureError)
            

          


          
        


        
        

          

            
EXPLOIT 4

            
Expired Token Replay

          

          

            An attacker intercepts an old token whose expiration timestamp (exp) is in the past and attempts to reuse it.
          


          

            payload.exp = now - 3600 (Expired 1 hour ago)
          


          

            

              Secure Verifier: 🛡️ PROTECTED (token_expired / 401)
